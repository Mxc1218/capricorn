# 未采纳的方案与待决问题

> 记录"想过但没做"的东西和原因。比记录"做了什么"更重要——
> 因为三个月后会想不起来为什么不那么做，然后重新踩一遍。

## P1. 规划者台账：显示"做到哪一步"（部分采纳，暂缓）

**现象（2026-11-20，e1-04）**

```
t003  登录认证与注入测试      done   36s   产出 2 条事实
t005  登录表单注入与认证绕测试  failed  0s   （从未起跑）
t004  页面源码与静态资源泄露分析 failed  0s   （从未起跑）
t006  登录页源码与静态资源分析  failed  0s   （从未起跑）
```

规划者会对"半成功"的方向**生成细化变体**（t003→t005、t004→t006）。
这不是瞎重复，是"上一次没做完，想带着更具体的指令重来"。

**原本的提案**

1. 台账里依据事实显示内容（不只是 id）
2. 算依据事实的 Jaccard 重叠度，给个提示
3. prompt 要求"必须说明与已有方向的区别"

**为什么没做**

- **Jaccard 提示没有意义**：同一批事实可以撑不同角度（f001 是登录表单，可派 SQLi/弱口令/CSRF），
  重叠度高不代表方向重复。用户原话："依据重叠，并不代表什么吧"。
- **prompt 硬要求**会增加模型工作量，效果存疑。
- 更根本的：问题的成因不是"没看清台账"，而是"重试被实现成了新建任务"。

**更可行的方向（待验证）**

- 台账里失败方向的 result 不再截断 100 字，把"做到哪、卡在哪"摊开
- planner 写 `retry_of: t003` → 新任务**注入上一次的结果摘要**（不合并 detail）
- 同一重试链最多 2 次，超了拒绝派发，强制换攻击面

**为什么暂缓**：

用户判断"加强原任务会让协作熵增大"——这是对的：
1. worker 的 brief 越叠越长，抓不住重点
2. 两次指令可能互相矛盾（"手工测"和"用 sqlmap"打架）
3. 复盘读不懂，一条任务的历史变成大杂烩

所以方向改成"独立任务 + 注入上下文"，但**还没验证**这样是否真的减少变体。
需要先有 a/b 系列的数据（e 系列太简单，不触发变体）。

## P2. 时间分档（probe_timeout）—— 等 b 系列验证后再迁

Cairn 的实现（`dispatcher/config.py` ExploreTaskConfig）：

```
第 1 档  从没产出过        → probe_timeout（短 Q 试探，如 300 秒）
第 2 档  已产出过 fact     → timeout（大 Q，复杂任务不被切碎）
第 3 档  零产出且超时耗尽   → 结案，不再派发
```

**为什么好**：方向存活中位 153 秒、p90 817 秒，方差极大，固定档位对一部分必然错得离谱。

**为什么暂缓**：升档会触发"关容器重开"，靶场地址会变、黑板要迁移。
那是个独立工程，要等 b 系列验证完（b 系列才需要长时间片）。

## P3. 覆盖标签去重（已否决）

最初提的：planner 给每条方向打 coverage 标签，代码按标签去重。

**否决理由**：
- LLM 打标签不一致（"登录绕过"可能写成 auth-bypass / login / sqli-login）
- **误合并的方向找不回来**，那片攻击面就没人管了；而漏合并只是浪费一个槽
- 代价不对称 ⇒ 宁可漏合并，不可误合并
